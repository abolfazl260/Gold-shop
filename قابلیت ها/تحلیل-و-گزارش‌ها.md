# تحلیل محصول، عملیات و اقتصاد هر سفارش

## تعاریف
- **GMV:** مجموع ارزش سفارش‌های معتبر طبق تعریف گزارش (ثبت/پرداخت/تحویل؛ تعریف دقیق باید انتخاب و روی نمودار درج شود).
- **Gross Platform Revenue:** کمیسیون و خدمات پلتفرم قبل از هزینه‌ها/بازپرداخت.
- **Net Platform Revenue:** درآمد پس از اصلاحات، برگشت‌ها و موارد مرتبط طبق تعریف مالی.
- **Take Rate:** درآمد تعریف‌شده پلتفرم ÷ GMV متناظر؛ مخرج باید با صورت و بازه یکسان باشد.
- **Conversion Rate:** تعداد خریداران/سشن‌هایی که به سفارش معتبر رسیدند ÷ جمع متناظر ورودی‌ها.
- **CAC:** هزینه قابل انتساب جذب ÷ تعداد مشتری جدید در بازه تعریف‌شده.
- **Cancellation/Dispute Rate:** شمار لغو یا اختلاف ÷ سفارش‌های متناظر؛ علت‌ها جدا باشند.

## رویدادهای محصول P0
| Event | زمان ارسال | فیلد نمونه امن |
|---|---|---|
| search_performed | جست‌وجو | category_id، filters_count، results_count |
| offer_viewed | نمایش صفحه | offer_id، seller_id، referrer |
| quote_requested | درخواست مبلغ | offer_id، quote_state |
| quote_accepted | پذیرش | quote_id، amount_bucket؛ نه PII |
| checkout_started | آغاز خرید | cart_items_count، seller_id |
| payment_initiated | تلاش پرداخت | payment_attempt_id، amount_bucket |
| payment_verified | تأیید مستقل PSP | order_id، amount_irr از backend |
| order_cancelled | لغو ثبت‌شده | order_id، reason_code |
| order_shipped / order_delivered | رخداد عملیاتی | order_id، carrier_type |
| ticket_opened / dispute_resolved | پشتیبانی | reason_code، duration_bucket |
| seller_onboarded / seller_suspended | تأیید یا تعلیق | seller_id، reason_code |
| settlement_reconciled | تطبیق مالی | settlement_id، match_status |

## داشبوردها
- **فانل مشتری:** مشاهده → جست‌وجو → محصول → quote → شروع پرداخت → پرداخت تأییدشده؛ جداسازی خطای فنی از ترک خرید.
- **سلامت فروشنده:** SKU منتشرشده و موجود، سرعت تأیید سفارش، لغو، اختلاف، تأخیر، کیفیت داده.
- **مالی:** GMV، کمیسیون قراردادی، هزینه پرداخت، هزینه حمل پلتفرم، بازپرداخت، بدهی/تسویه و اختلاف PSP.
- **عملیات:** نرخ منقضی، سفارش PAYMENT_UNKNOWN، رزروهای گیرکرده، ارسال‌های تأخیردار، تیکت‌های SLA عقب‌افتاده.

## اهداف اولیه آزمایشی
- هیچ order پرداخت‌شده‌ای بدون ارجاع معتبر PSP نباشد.
- هیچ پرداخت/تسویه مضاعف بدون شناسایی و مسیر اصلاح نباشد.
- خطاهای مغایرت موجودی، نرخ و فاکتور به‌صورت روزانه گزارش شوند.
- شاخص‌های تجاری (CAC، تبدیل، تحویل، رضایت) بعد از پایلوت **بر مبنای داده واقعی** هدف عددی بگیرند.

## حریم خصوصی و صحت
- داده تحلیلی حداقلی و بدون شماره موبایل، نشانی، مدارک یا اطلاعات کارت.
- عدد درآمد از ledger/reconciliation می‌آید؛ analytics کلاینت مرجع تراکنش مالی نیست.
- bot traffic، retry و event duplicate در قیف حذف/علامت‌گذاری شوند.
- بر هر گزارش تاریخ، بازه، currency unit، timezone و تعریف metric درج شود.
